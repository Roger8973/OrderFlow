## Purpose

Lets salespeople register customers so that orders can later be created for them. This capability covers the customer registry and its data rules; retrieval, listing, and deactivation are added by later changes.

## ADDED Requirements

### Requirement: API registers a new customer
The system SHALL expose a `POST /customers` endpoint that accepts a customer `name`, `email`, and optional `phone` as a JSON body and, on success, creates the customer and responds with HTTP 201 and a JSON body containing the created customer's `id`, `name`, `email`, `phone`, and `isActive`.

#### Scenario: Customer is created with all fields
- **WHEN** a client sends `POST /customers` with a valid `name`, a valid `email`, and a `phone`
- **THEN** the system responds with HTTP 201
- **THEN** the response body contains a system-generated `id` and echoes the submitted `name`, `email`, and `phone`

#### Scenario: Customer is created without a phone
- **WHEN** a client sends `POST /customers` with a valid `name` and `email` and no `phone`
- **THEN** the system responds with HTTP 201
- **THEN** the response body reports `phone` as null

#### Scenario: Client-supplied id is ignored
- **WHEN** a client sends `POST /customers` with an `id` property in the body
- **THEN** the created customer's `id` is generated by the system and differs from the supplied value

### Requirement: New customers are active
The system SHALL create every new customer in the active state.

#### Scenario: Customer is active after creation
- **WHEN** a client successfully creates a customer
- **THEN** the response body reports `isActive` as true

### Requirement: Customer data is validated
The system SHALL reject a create-customer request with HTTP 400 and an RFC 7807 problem-details body that identifies each invalid field when: `name` is missing, blank, or longer than 200 characters; `email` is missing, blank, not a well-formed email address, or longer than 254 characters; or `phone` is longer than 30 characters. Surrounding whitespace in `name`, `email`, and `phone` SHALL be trimmed before validation and storage, and a blank `phone` SHALL be treated as absent. No customer SHALL be created when validation fails.

#### Scenario: Name is missing
- **WHEN** a client sends `POST /customers` without a `name`
- **THEN** the system responds with HTTP 400 with a problem-details body that reports an error for `name`
- **THEN** no customer is created

#### Scenario: Name is blank
- **WHEN** a client sends `POST /customers` with a `name` consisting only of whitespace
- **THEN** the system responds with HTTP 400 with a problem-details body that reports an error for `name`

#### Scenario: Email is malformed
- **WHEN** a client sends `POST /customers` with an `email` that is not a well-formed email address
- **THEN** the system responds with HTTP 400 with a problem-details body that reports an error for `email`
- **THEN** no customer is created

#### Scenario: Field exceeds maximum length
- **WHEN** a client sends `POST /customers` with a `name` longer than 200 characters, an `email` longer than 254 characters, or a `phone` longer than 30 characters
- **THEN** the system responds with HTTP 400 with a problem-details body that reports an error for each offending field

#### Scenario: Multiple fields are invalid
- **WHEN** a client sends `POST /customers` with both a blank `name` and a malformed `email`
- **THEN** the system responds with HTTP 400 with a problem-details body that reports errors for both `name` and `email`

#### Scenario: Surrounding whitespace is trimmed
- **WHEN** a client sends `POST /customers` with `name` "  Maria Silva  " and `email` " maria@example.com "
- **THEN** the system responds with HTTP 201
- **THEN** the response body contains `name` "Maria Silva" and `email` "maria@example.com"

### Requirement: Customer email is unique
The system SHALL NOT allow two customers to share the same email address. Email uniqueness SHALL be case-insensitive, and the created customer's `email` SHALL be reported in lower case. A create-customer request with an email already in use SHALL be rejected with HTTP 409 and an RFC 7807 problem-details body, and no customer SHALL be created. This rule SHALL hold even when duplicate requests are processed concurrently.

#### Scenario: Duplicate email is rejected
- **WHEN** a customer with email "maria@example.com" exists and a client sends `POST /customers` with the email "maria@example.com"
- **THEN** the system responds with HTTP 409 with a problem-details body
- **THEN** no additional customer is created

#### Scenario: Duplicate email differing only by case is rejected
- **WHEN** a customer with email "maria@example.com" exists and a client sends `POST /customers` with the email "Maria@Example.com"
- **THEN** the system responds with HTTP 409 with a problem-details body

#### Scenario: Email is reported in lower case
- **WHEN** a client sends `POST /customers` with the email "Maria@Example.com" and no such customer exists
- **THEN** the system responds with HTTP 201
- **THEN** the response body contains the `email` "maria@example.com"

#### Scenario: Concurrent duplicate requests
- **WHEN** two clients simultaneously send `POST /customers` with the same email and no such customer exists
- **THEN** exactly one request responds with HTTP 201 and the other responds with HTTP 409
- **THEN** exactly one customer with that email exists

### Requirement: Customer creation is persisted
The system SHALL persist a created customer durably so that it remains stored after the response is returned and after the API restarts.

#### Scenario: Created customer survives a restart
- **WHEN** a client successfully creates a customer and the API is later restarted against the same database
- **THEN** the customer is still stored, and a subsequent create with its email is rejected with HTTP 409

### Requirement: Customer creation is documented in the API description
The system SHALL describe the create-customer endpoint, its request body, and its 201, 400, and 409 responses in the generated OpenAPI document.

#### Scenario: Endpoint appears in OpenAPI
- **WHEN** a client retrieves the generated OpenAPI document
- **THEN** it contains a `POST /customers` operation documenting the request body and the 201, 400, and 409 responses
